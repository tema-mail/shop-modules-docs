Как устроен shop-modules

← Обзор стека · Полная архитектура → · ADR-002: живые процессы и логи →

Модульная система для интернет-магазинов: клиенты, каталог, заказы, бонусы, статусы, рефералы, промокоды, доставка, оплата. Подключается к сайту магазина на Astro. Эта страница – карта для разработчика: что из чего состоит, как ходят данные, где что лежит в коде. Подробности и решения – в архитектуре.

Коротко

Правила денег – чистые функции в modules/<модуль>/rules.ts: без базы и сети, покрыты тестами, включая проверки свойствами на тысячах случайных примеров. Вокруг них – слой хранения и API. Процессы (оформление, оплата, завершение, отмена, возврат) описаны графом и исполняются движком по этому графу, каждый шаг пишется в журнал.

Сейчас готово: все правила, движок процессов, демо-магазин, где «сервер» работает в браузере. Следующий этап: настоящий сервер (Fastify + PostgreSQL) на тех же правилах, затем оплата, доставка и логи.

  • Деньги – только целые копейки (bigint), проценты – базисные пункты (1 % = 100). Кешбэк округляется вниз, скидки разносятся по строкам без потери копеек.
  • Журнал баллов только дописывается: состояние «ожидает → подтверждён → аннулирован» выводится из последующих проводок. Баланс = подтверждённое − удержанное.
  • Настройки версионируются: заказ хранит версию правил, возврат и подтверждение считаются по ней.

5. Процессы графом

Сделано (ADR-002, этапы 1–3): пять процессов (оформление, оплата, завершение, отмена, возврат) – схемы-данные в modules/orders/flows-v2.ts. Движок packages/kernel/flow-v2.ts исполняет ровно проверенную и замороженную схему: действие возвращает факты, ветку выбирает условие схемы. Страница «Процессы» рисует граф из тех же объектов. Заказ закреплён за версией набора процессов.

Сделано (этап 4): редактор процессов в админке – форма «шаги и переходы» над черновиком (packages/kernel/flow-edit.ts), живая проверка и превью; публикация набора – разница с прошлой версией и все пути (flow-diff.ts), журнал опубликованных версий, выгрузка JSON для git. Новые заказы идут по последнему набору, оформленные доигрывают по своему.

Кто что решаетКак
Порядок шагов и веткисхема (данные): узлы ссылаются на действия из реестра, переходы – условия на JSON Logic над фактами шагов
Что делает шагкод действия из реестра: проверяет свои предусловия, работает с ключом повтора, возвращает факты (total_is_zero, delivery_mode…)
Деньгитолько код действий; в условиях – белый список операторов JSON Logic (var, ==, !=, in, and, or, !), сумм и арифметики нет – плохая схема может остановить процесс, но не испортить деньги
Версиипубликуется набор из пяти процессов целиком; заказ закрепляется за набором при создании и все его процессы идут по нему; опубликованные версии неизменяемы и выгружаются в git
Защита денег от правки схемыденежные действия объявляют нужное состояние заказа (например, «оплачен») и проверяют его в базе; денежные развилки («сумма 0 ₽», «оплачен ли») закрыты для редактора; проверка набора: каждое удержание и начисление чем-то закрывается
Почему не BPMN / n8nBPMN-движки для Node нишевые и хранят условия JS-строками; в n8n и похожих в шаг можно написать любой код – денежный контур не удержать

Пример узла и перехода в схеме:

{ "id": "zero_total", "action": "orders.checkZeroTotal" }
{ "from": "zero_total", "to": "start_payment", "when": { "==": [ { "var": "total_is_zero" }, true ] }, "locked": true }
{ "from": "zero_total", "to": "await_payment", "else": true, "locked": true }
Правило проверки схемыЧто не даёт сделать
форма, циклы, недостижимые шаги, полнота и перекрытие ветокпроцесс, который зависнет или выберет две ветки сразу
условие – только на факты шагов, пройденных на всех путях (доминаторы)ветку по факту, которого ещё нет
locked + lockedNodesпоменять денежную развилку или действие на её концах
actions процессавставить «заказ оплачен» в оформление
required – на всех путях к каждому концуубрать удержание баллов или спрятать его в одну ветку
mustPrecedeсписать баллы до оплаты, удержать после создания заказа
requires у денежного действия (в рантайме, по статусу заказа)выполнить деньги в неверном состоянии, даже если схема пропущена
сквозная проверка набора (flow-set.ts)удержание, кешбэк, промокод или резерв, которые нигде не закрываются

6. Логи и наблюдаемость

Сейчас: бизнес-журнал процессов (step_runs) – каждый шаг заказа с кодом ошибки, виден на странице «Процессы» демо. Модуль структурных логов готов (packages/kernel/log.ts: pino, одна строка JSON, сквозные поля, вырезание ПДн и секретов), подключается вместе с сервером.

Решено (ADR-002, с первым шагом сервера): структурные логи; на боевом сервере – распространённый лёгкий стек Grafana (Loki), на тестовом стенде – VictoriaLogs (около 0,1 ГБ памяти, свой поиск), потому что стенд делит сервер с другими проектами. ELK не берём: ему нужно 3–4 ГБ памяти.

Поля названы по стандарту OpenTelemetry: трассы и метрики подключаются позже без переделки логов.
