# ADR-004 (версия 2, 16.10.2026): закрытый боевой магазин – сервер, админка магазина, персонал

Повод – решение владельца: «делаем полностью боевой магазин… как закрытый боевой магазин»: он сам проходит оплаты, СДЭК, отмены и возвраты на настоящих тестовых контурах, потом магазин открываем. И: «админ-панель магазина: видеть клиентов, ставить и убирать баллы, удалять клиента, управлять пользователями».
Версия 1 получила FAIL у ревизора архитектуры (20 замечаний, 5 критичных: блокировка чужой таблицы, пропущено ядро ADR-001, «коды входа в админке» = захват учёток, перебор кодов, админка на одном origin с витриной); версия 2 – ещё 3 противоречия (права на журналы и стирание, порядок обработчиков); все внесены ниже.

Источники: разведка проекта; прототип на действующем магазине: админа не было, правки руками в таблице – начисление без причины и автора, нет уникальности почты, списание без проверки баланса, вебхуки без подписи и идемпотентности; практика рынка – Shopify (store credit, erase customer data, order status), Saleor (права групп), Square (adjust points), Medusa и Vendure (заказ как автомат, изменение заказа), Talon.One (минус на балансе), OWASP (2FA, журнал), Т-Банк (уведомления, Cancel, тестовые карты), 152-ФЗ ст. 6, 9, 18, 21, 22, 54-ФЗ.

## 1. Сервер и окружение

В демо «сервер» живёт в браузере – админка в нём видела бы только клиентов своего браузера. Поэтому админка строится на сервере (этап 5 ADR-001/002); демо остаётся витриной для показа.

- **Закрытая бета** – VPS Beget (РФ), тот же, что у стенда. **На бете только сотрудники и тестировщики с письменным согласием на обработку ПДн; реальные клиенты – только на боевом VPS** (этап 8). Соседи по VPS с доступом к docker.sock фактически root – признанный риск беты (ADR-002, C).
- **Адреса**: витрина `store.deford.ru`; **админка – отдельный origin `admin.store.deford.ru`** (XSS на витрине не даёт доступа к админке); API – `store.deford.ru/api/*` и `admin.store.deford.ru/api/*` (отход от `api.<домен>` из ADR-001: один сервис, два origin с разными cookie и CSP).
- **Сервис**: `apps/api` – Fastify 5 + Zod, api и worker (pg-boss) одним процессом на бете; PostgreSQL 18 в контейнере. Память (общий лимит стенда ≤1,2 ГБ): Postgres `shared_buffers` 128 МБ, `max_connections` 20, `mem_limit` 384 МБ; api+worker ≤256 МБ; VictoriaLogs 128 МБ; Mailpit ~30 МБ; ротация логов Docker.
- **Роли БД**: миграции – `shop_owner` (владелец таблиц), приложение – `shop_app` без прав владельца; у `shop_app` на журналах (`ledger`, `staff_audit`, `flow_sets`, `step_runs`) только INSERT и SELECT (тест: UPDATE – permission denied). Отключить триггер приложение не может. Стирание ПДн при обезличивании там, где у `shop_app` нет UPDATE (задачи pg-boss, полезная нагрузка outbox), – функции `SECURITY DEFINER` владельца `shop_owner`, их вызывает обработчик `customer.erased`.
- **Секреты** – файлы с правами 600 вне git (`/opt/shop-api/secrets/`), в окружение при старте: пароли БД, ключ шифрования TOTP, HMAC-секрет почт, ключ шифрования бэкапов. Ротация – процедурой (раздел 9).
- **Бэкап с первого дня данных**: ежесуточный `pg_dump`, шифрованный age, не на диске VPS: забирается на мак владельца (в РФ, FileVault, папка вне iCloud Drive, мак внесён в перечень мест обработки ПДн); хранится ≤30 дней (стёртые данные не живут в бэкапах дольше срока по 152-ФЗ). Раз в неделю – восстановление в отдельную базу и сверка сумм баллов. На бою – pgBackRest в S3 в РФ (ADR-001/002).
- **Наблюдаемость**: pino → VictoriaLogs; GlitchTip и Uptime Kuma на стенде; `pino.redact` для пароля, TOTP и кодов входа.

## 2. Учёт баллов на сервере (как ADR-001)

- Таблицы модуля bonus – `ledger` (журнал проводок) и `holds`; модуль не трогает чужих таблиц.
- Журнал только дописывается (права `shop_app` + триггер), ключ повтора – уникальный индекс.
- Баланс – из журнала («баланс = журнал − удержания»); кэш допускается, перестраивается и сверяется ночью.
- Списание (оформление, ручное) – в транзакции под `pg_advisory_xact_lock` по клиенту: два параллельных списания не пройдут оба. Части одного ручного списания – одной транзакцией.
- Ручные операции – `grantPoints` / `debitPoints` (modules/bonus): причина – из готового списка («компенсация», «ошибочное начисление», «акция», «другое»), её видит клиент; внутренний комментарий сотрудника – в отдельной таблице `staff_audit_notes` (UPDATE разрешён – стирается при обезличивании), сам `staff_audit` неизменяем. Ключ `manual:<код>` генерируется при открытии формы и уходит как Idempotency-Key – двойной клик не даёт двух проводок.
- Минус на балансе – только от возвратов (сторно уже потраченного кешбэка), не сгорает, гасится будущими начислениями. Ручное списание в минус не уводит. Окончательное правило «баллы потрачены, а заказ вернули» – решение владельца (сейчас: минус).

## 3. Персонал и вход в админку

- Своя учётка у каждого; общих нет. Роли (права группами): **владелец** – всё; **менеджер** – клиенты, баллы, заказы; **поддержка** – просмотр клиентов и заказов (почта и телефон замаскированы, полный показ – с записью в аудит), без баллов и удаления. Просмотр истории баллов и экспорт – отдельные права.
- Пароль: argon2id (m = 19 МиБ, t = 2). **2FA TOTP обязательна**; секрет шифруется ключом из окружения; один код принимается один раз; 10 кодов восстановления (хранятся хешами).
- Первый владелец и сброс 2FA владельца – CLI на сервере, с записью в аудит. Пароль сотрудника сбрасывает владелец: временный, смена при входе.
- Сессия: 12 ч абсолютно + 30 мин простоя; отключение сотрудника и «выйти везде» закрывают сессии. Повторный TOTP – для обезличивания, экспорта, смены ролей, сброса 2FA, возврата денег.
- Cookie `__Host-`, Secure, HttpOnly, SameSite=Strict; CSRF – проверка Origin и свой заголовок для JSON; CSP без inline (хеши Astro), `frame-ancestors 'none'`; `@fastify/rate-limit` на вход сотрудников.
- Админка закрыта целиком; на бете домен дополнительно за паролем стенда.

## 4. Журнал действий персонала

Таблица `staff_audit` (у `shop_app` только INSERT/SELECT): когда, кто, что (`customer.points.grant`, `customer.ban`, `customer.erase`, `order.cancel`, `staff.role.change`, `export`…), с кем (id), причина, результат; внутренний комментарий – в `staff_audit_notes`. Без паролей, токенов и ПДн клиента. Действие и запись аудита – в одной транзакции; отказы в доступе – отдельной транзакцией. Ночная копия аудита – в VictoriaLogs (соседи по VPS – root). Просмотр – владелец.

## 5. Клиенты

- Список: поиск (почта, имя, телефон, id), фильтры (статус лояльности, бан, «требует внимания», дата регистрации), итоги (заказов, оплачено, баланс, статус). Сегменты правилами – позже.
- Карточка: профиль, адреса, заказы, баллы (баланс и история), рефералы, промокоды, аудит по клиенту.
- **Начислить / списать баллы** – раздел 2.
- **Бан в программе** (не «блокировка ПДн» по 152-ФЗ): нельзя войти и оформить заказ, сессии закрываются, новых начислений нет; по уже оформленным заказам кешбэк не начисляется (они доигрывают по процессу, шаг начисления пропускается по факту «клиент забанен»). Причина обязательна.
- **Уникальность почты** – уникальный индекс по нормализованной почте.
- **Обезличивание по запросу** (152-ФЗ, ст. 21: отзыв согласия – 30 дней): модуль customers публикует событие `customer.erased`; **каждый модуль стирает своё** (customers – профиль, адреса, сессии, коды; orders – снимок доставки и получатель; payments – почта и телефон в чеках `Receipt`; notifications – адреса писем; outbox и задачи pg-boss – полезная нагрузка через функции владельца) – тест на каждый модуль. Журнал шагов `step_runs` (ядро) ПДн не содержит – только id и коды (ADR-001, тест redact), стирать в нём нечего. Обработчик `customer.erased` появляется в модуле вместе с самим модулем (шаг S6f – customers и outbox; orders – S7, payments – S10, notifications – S3b и S11), каждый с тестом. Заказы, суммы и журнал баллов остаются без ПДн (первичные документы – 5 лет); `consents` остаётся с отметкой отзыва без ПДн.
  - Сразу стирается всё, кроме данных незавершённых заказов (основание – исполнение договора, ст. 6 ч. 1 п. 5); остаток стирается по завершении заказа; срок 30 дней контролируется по журналу.
  - Защита от повторного приветственного бонуса той же почтой – HMAC-SHA256(почта, секрет из окружения), не простой хеш; основание – ст. 6 ч. 1 п. 7 (законный интерес, прописать в политике); срок хранения – константа, после него запись удаляется.
- **Вход клиента по коду**: код хранится только хешем, живёт 10 мин, 5 попыток; запрос кода – ≤3 за 15 мин на почту и ≤20 в час на IP; проверка – ≤10 неверных в час на почту; ответ одинаковый для существующей и несуществующей почты; `@fastify/rate-limit` на `/api/*`.

## 6. Заказы

- Статус оплаты и статус выдачи – раздельно: оплата – из попыток (ADR-003), выдача – собирается / передан в доставку / выдан / возврат.
- «Требует внимания»: записи `attention` (ADR-003) – оплата после отмены, возврат денег не прошёл, банк молчит, адрес не принят.
- Действия магазина: передать в доставку, отметить выдачу, отменить с возвратом (Т-Банк Cancel с `ExternalRequestId`; при частичной отмене – `Receipt` с позициями), частичный возврат – «изменение заказа», подтверждается целиком.

## 7. Письма на бете

Письма (код входа, уведомления) идут через адаптер `notifications`; на бете адаптер шлёт в **перехватчик Mailpit** (`mail.store.deford.ru`, за паролем стенда): тестировщик или владелец видит письмо там. Режим задаёт константа `MAIL_SINK`; при `env=prod` запуск с ней падает (тест). После регистрации сервиса рассылки (Yandex Cloud Postbox или Unisender Go – владелец) адаптер переключается на него.

## 8. Закрытая бета – что проверяем перед открытием

Тестовые карты Т-Банка (успех, 3-D Secure, отказ, нехватка средств); отмена и частичный возврат с чеком; уведомления банка с проверкой `Token` и ответом `OK`, повтор уведомлений (второго начисления нет); СДЭК – заявка, отмена, статусы; письма; остатки; бэкап с восстановлением; алерты; 2FA у всех сотрудников; процедура утечки; уведомление РКН по ст. 22 – до боевого запуска.

## 9. Процедура утечки

Кто действует – владелец (замещающий – назначить); шаги: закрыть дыру, отозвать все сессии клиентов и сотрудников, ротировать секреты (БД, TOTP-ключ, HMAC, ключи провайдеров), уведомить РКН – за 24 ч первично и за 72 ч по итогам расследования (ст. 21 ч. 3.1), сохранить журнал. Документ процедуры – до боевого запуска.

## 10. Порядок работ (каждый шаг – ≤3 файлов кода, ревизор, коммит)

| Шаг | Что | Проверка |
|---|---|---|
| S1a | `apps/api`: Fastify, `/api/health`, логи pino, конфиг | тест health; сборка |
| S1b | Раннер миграций, роли `shop_owner`/`shop_app`, журналы «только дописывать» | миграции применяются, повтор ничего не ломает; приложение не переписывает журнал (Postgres 18 в CI) |
| S1c | Postgres в compose стенда с лимитами памяти и обёрткой init; выкладка api на стенд за Caddy; бэкап age + забор на мак + проверочное восстановление; Uptime Kuma | `/api/health` снаружи за паролем; восстановление из дампа |
| S2a | `001_kernel.sql`: idempotency, outbox, module_settings, secrets (ADR-001, п. 2) | тесты на Postgres 18 в CI |
| S2b | Диспетчер outbox → pg-boss | тест «событие ровно один раз после сбоя» |
| S2c | Настройки модулей на сервере | тест «правило на момент заказа» |
| S3a | Клиенты: таблицы, нормализованная почта, уникальный индекс | тесты |
| S3b | Вход по коду: хеш кода, лимиты, сессии; письма через `notifications` в Mailpit | тесты на лимиты и одинаковый ответ |
| S4 | Баллы на Postgres: `ledger`, `holds`, триггер, права, advisory lock | тест: два параллельных списания – одно проходит (Postgres в CI) |
| S5a–c | Персонал: учётки и роли; пароль + TOTP + коды восстановления + CLI владельца; сессии и `staff_audit` | тесты: без 2FA не войти; «поддержка» не списывает баллы; отказ пишется в аудит |
| S6a–f | Админка «Клиенты» на `admin.store.deford.ru`: каркас (эталон Elite Rose) / список / карточка / баллы / бан / обезличивание (событие `customer.erased`; стирание в customers и outbox, в остальных модулях – по мере их появления) | живая проверка; admin-acceptor |
| S7a–e | Заказы на сервере: catalog + quote / place / `flow_sets` + процессы v2 / попытки оплаты + attention / `ShopPort` – витрина работает через API, демо на Pages – через локальный движок | сквозные тесты на Postgres |
| S8 | Админка «Заказы» (эталон ALEX KROWN) и «Требует внимания» | живая проверка |
| S9 | СДЭК – учебный контур | заявка, отмена, статусы |
| S10 | Т-Банк – тестовый терминал (нужен от владельца), чеки | тестовые карты, отмена, возврат |
| S11 | Сервис рассылки (нужен от владельца), процедура утечки, GlitchTip | письмо с кодом на настоящую почту |

**Тесты**: юнит – Vitest; всё, что про конкуренцию, триггеры и права БД, – только на настоящем Postgres 18 (в CI, Docker на маке нет); PGlite – только для быстрых юнит-тестов SQL. **Витрина на API** – через асинхронный порт `ShopPort` с двумя реализациями (локальный движок для демо на Pages, HTTP для стенда), выбор константой сборки, перевод по экрану за шаг.
