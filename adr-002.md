# ADR-002 (версия 2 после ревизии, 16.10.2026): исполняемые процессы, логи, стенд

Повод – замечания тимлида: (1) граф «неживой» – схема должна исполняться, правка в интерфейсе меняет порядок действий без кода; (2) не видно, где логи – нужен распространённый стек; (3) документация непрозрачна.
Версия 1 получила FAIL у architecture-reviewer (12 замечаний), все внесены ниже. Ход работ: этапы 0–4 сделаны (16.10.2026) – план этапа 4 в ПЛАН-РЕДАКТОР.md; стенд 6a/6b готов к выкладке и ждёт DNS. ADR-002 заменяет в ADR-001 (АРХИТЕКТУРА.md): «граф только для просмотра», «граф – React-остров xyflow», «GlitchTip и Uptime Kuma, Loki позже», «Caddy» для стенда.

## A. Процессы: граф как данные

Сейчас: узлы и рёбра в коде (`modules/orders/flows.ts`), ветку выбирает обработчик (возвращает метку); переход «оформление → оплата» для заказа на 0 ₽ запускает код, а не граф.

Решение: свой JSON-граф + условия переходов на JSON Logic + реестр действий в коде.

**Исполнение**
- `kernel/flow-v2.ts` рядом с v1: `runFlowV2(def, registry, ctx)`. Действие возвращает **факты** (типизированный объект); переход выбирает движок по `edge.when`: истинно ровно одно ребро или срабатывает «иначе»; 0 или 2 истинных – `route.none` / `route.ambiguous` и стоп.
- Условия – белый список операторов JSON Logic: `var, ==, !=, in, and, or, !`. Арифметики и сумм нет; факты – boolean/enum, их считает код. Валидатор отклоняет схему с другими операторами.
- Переходы между процессами (оформление → оплата при 0 ₽, оплата → доставка) описываются в графе как узел-переход, а не скрытым кодом.

**Защита денег от правки схемы**
- Денежные действия объявляют `requires` – состояние заказа, без которого они не выполняются (`paid` для списания баллов, начисления кешбэка, возврата денег; `awaiting_payment` для снятия удержания; `settled` для подтверждения кешбэка). Проверка – в рантайме по состоянию заказа в базе, с тестом на каждое правило.
- Рёбра денежных развилок (сумма 0 ₽, «оплачен ли» в отмене, «завершён ли» в возврате) закрыты для редактора: их условия задаёт код.
- Порядок шагов проверяется анализом доминаторов: обязательный шаг стоит на **всех** путях до зависимого, а не на одном. Тем же правилом – «условие ссылается на факты шагов, которые выполнены на всех путях до него».

**Версии**
- Публикуется **набор** из пяти процессов заказа целиком (`flow_sets(version)`), опубликованные версии неизменяемы.
- Заказ закрепляется за набором при создании (`orders.flow_set_version`) и все его процессы – оформление, оплата, завершение, отмена, возврат – идут по этому набору.
- Сквозная проверка набора: каждое удержание и начисление закрыто хотя бы одним путём (`hold` → `commit`/`release`, `accrue` → `confirm`/`void`).
- Публикация: черновик → валидатор → прогон всех путей на тестовых данных → разница с прошлой версией → публикует владелец → аудит. Каждая опубликованная версия выгружается в git (`flows/<версия>.json`) – логика не живёт только в базе.

**Идемпотентность**
- Ключи строятся только из id объектов (`orderKeys(orderId)`, `returnKeys(returnId)`); `node_id`, `run_id`, `flow_version` в ключ не входят. Тест: повтор шага после смены версии не даёт второй проводки.
- Остатки, промокоды и отгрузка идемпотентны проверкой состояния; для СДЭК и Т-Банка – ключ на стороне провайдера (номер заказа).

**Редактор**: шаг 1 – форма «узлы и переходы» на Preact с превью на нашем SVG; перетаскивание (xyflow через preact/compat) – только после пробного прототипа.

**Миграция без поломки демо**: `runFlowV2` в новом файле; адаптер «метка → факт `{route}`»; перенос по одному процессу при зелёных сквозных тестах; v1 удаляется последним шагом.

Отклонено: BPMN (bpmn-js + bpmn-engine) – движок нишевый, условия JS-строками, обязательный водяной знак; n8n / Windmill / Camunda – в шаг можно написать любой код, денежный контур не удержать.

## B. Логи и наблюдаемость

- pino → JSON в stdout; поля по OpenTelemetry: `ts, level, service, shop, env, version, trace_id, order_id, flow_id, flow_version, run_id, node_id, action, status, error_code, duration_ms, http.route, http.status, provider, attempt`.
- ПДн и секреты в логи не попадают: `pino.redact` + тест (email, телефон, ФИО, адрес, токены, карта).
- **Стенд**: VictoriaLogs (Apache-2.0, ~0,1 ГБ RAM, встроенный интерфейс поиска) – Loki с Grafana на общем VPS не помещаются в лимит памяти.
- **Прод**: Grafana Alloy → Loki → Grafana (≈0,5–0,8 ГБ RAM); метки только `service, env, shop, level`; `order_id` – поле; панели «заказ по id», «ошибки», «внешние API»; алерты в Telegram без ПДн; хранение 14 дней.
- Лицензии: Loki и Grafana – AGPL-3.0; ставим как отдельные процессы без изменений, не форкаем и не встраиваем в свой код. (n8n и Windmill отклонены не за лицензию, а за код в шагах.)
- GlitchTip остаётся для исключений, Uptime Kuma – для доступности; оба на проде.
- `step_runs` остаётся бизнес-журналом процессов в админке.

## C. Размещение и защита

- **Стенд**: текущий VPS Beget (2 vCPU, 4 ГБ, свободно ~2 ГБ, 9,8 ГБ диска); `mem_limit` на каждый контейнер, всё вместе ≤1,2 ГБ. Впереди – уже работающий на сервере общий Caddy (порты 80/443 его): свой блок в общем Caddyfile, сертификат Caddy выпускает сам. Контейнеры стенда не публикуют порты – Caddy ходит к ним по docker-сети; секреты в файлах с правами 600. Выкладка – `deploy/stand/deploy.sh` (блок между метками, проверка конфигурации и откат).
- **Только синтетические данные на стенде**: реальных клиентов не загружаем; у соседних проектов с доступом к docker.sock фактически root – это признанный риск стенда. Тестовые ключи провайдеров не совпадают с боевыми. Бэкап стенда не выносится в общий S3.
- **Прод**: отдельный VPS в РФ (2 vCPU, 4 ГБ, от 40 ГБ NVMe), Caddy 2, бэкапы pgBackRest в S3 в РФ с проверкой восстановления раз в месяц.
- Домен: store.deford.ru, в Cloudflare только DNS (серое облако) – прокси режется в РФ и уводит ПДн за рубеж; сертификат – Caddy (ACME).
- Закрытие стенда: basic auth в Caddy на всём, кроме robots.txt; `X-Robots-Tag: noindex, nofollow`, robots `Disallow: /`, заголовки безопасности и CSP. Пути вебхуков исключаются из basic auth на этапе 7 (подпись и перепроверка статуса у провайдера).
- **Вебхуки – только подсказка**: до любого денежного шага статус перепроверяется запросом к API провайдера (Т-Банк `GetState`, статус заказа СДЭК, Яндекс `request/info`). Подпись проверяется, где она есть (Т-Банк – поле `Token`, уточнить по официальной документации); для СДЭК – секрет в пути URL. Повторные вебхуки отсекаются по id события.
